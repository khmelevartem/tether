изучи issue <issue number>. оцени, все ли готово к ее выполнению, нет блокеров?

если готово — перед реализацией:

1. **проверь готовность продуктовой спеки** (только для типа FEATURE; для BUGFIX / REFACTOR / INFRA / DOCS / DEPENDENCY этот шаг пропускается).

   - если issue ссылается на файл в `docs/product/features/` — прочитай его.
   - если issue не ссылается на спеку — поищи фичу в `docs/product/features/README.md`. Колонка `Issues` должна содержать номер этой задачи; колонка `Doc` укажет путь к спеке.
   - если спеки нет ни там, ни там — **остановись**. Не начинай реализацию. Предложи пользователю сначала проработать спеку (создать файл в `docs/product/features/` и завести строку в индексе). Объясни, что без спеки нет источника истины по acceptance criteria и out of scope, и риск уйти не туда — высокий.
   - если спека найдена — **прочитай её внимательно** и оцени:
     - **заполнена ли она достаточно** для старта реализации, или это `(stub)` с заглушками. Stub — основание остановиться и предложить дописать спеку до начала работы.
     - **какие open questions блокируют старт**, а какие можно оставить на потом. Блокирующие — те, без ответа на которые нельзя написать код или нельзя проверить acceptance. Откладываемые — те, которые касаются деталей будущих этапов или edge cases, не влияющих на основной поток.
     - **есть ли в спеке указания на реализации той же фичи на других платформах** (типичный случай: «#7 (Android); iOS, Desktop _tbd_»). Если есть:
       - посмотри, можно ли взять одну из готовых реализаций как образец (стиль, структура слоёв, тестовый паттерн).
       - заметь, что после выполнения текущей задачи может понадобиться **дописать** в спеку или в смежные tbd-задачи: что готово в common-части и от чего теперь можно отталкиваться. Это часть результата задачи, не отдельный этап.

   только после того, как спека готова и понята, переходи к шагу 2.

2. **верифицируй root cause (только для типа BUGFIX).**

   Если в issue есть раздел «Гипотезы о причинах» / «Возможные причины» / список candidate-объяснений — это **непроверенные** догадки автора issue, не факт. До написания PR обязательно подтверди реальный root cause:

   - воспроизведи баг локально (`/smoke-test` или ручной сценарий из «Воспроизведение»);
   - проверь каждую гипотезу через минимальный эксперимент — логи, `tcpdump`/`logcat`, дебаггер, lsof, sysadmin-инструменты;
   - зафиксируй подтверждённую причину **комментарием в issue** до начала кодинга, чтобы у ревьюера и у тебя самого был общий контекст;
   - если ни одна из гипотез не подтверждается — **остановись**, отчитайся пользователю, обсуди дальнейшие шаги. Не пиши код «по первой гипотезе».

   Это критичный шаг: если взять непроверенную гипотезу как факт, можно написать корректный с виду фикс, который не решает реальную проблему — а понять это получится только на стадии manual verification, потеряв несколько сессий работы.

   Для FEATURE / REFACTOR / INFRA / DOCS / DEPENDENCY этот шаг пропускается.

3. загляни в `docs/engineering/` — там зафиксированы архитектурные принципы, схема модулей и правила DI. как минимум прочитай `dependency-injection.md` (там чек-лист «подходит ли мой код»). если задача затрагивает слои / новые компоненты / то, что хочется выделить в модуль — прочитай также `architecture-principles.md` и `modules.md`.

4. составь план реализации и стратегию валидации. явно отметь, если что-то в технических деталях issue вызывает сомнение или конфликтует с гайдами в `docs/engineering/` — не переделывай молча, а покажи альтернативу.

5. дождись ОК от пользователя, потом реализуй по гайду в `CLAUDE.md`.
