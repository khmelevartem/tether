> **Manual fallback.** По умолчанию используй `/implement <issue>` — он оркеструет этот же процесс через сабагентов и не дёргает тебя на каждой итерации coder↔reviewer. Эта команда — пошаговый чек-лист для случаев, когда хочешь пройти процесс руками: отладка самого оркестратора, нестандартная семантика задачи, эксперимент.

изучи issue <issue number>. оцени, все ли готово к ее выполнению, нет блокеров?

**Воспринимай описание issue как стартовую точку, не как факт.** Подсвечивай и эскалируй пользователю до начала работы, если видишь хотя бы один пробел:
- упомянута только одна платформа, хотя задача общая;
- не описаны ошибки и fail-paths;
- непонятно, как тестировать (нет указаний на edge cases / runtime check);
- BUGFIX без хотя бы предполагаемой причины бага;
- фразы-затычки: «дополни если есть чем», «должно работать корректно», «и так далее».

Любой такой пробел — повод остановиться и попросить доработать issue, а не «допилить по дороге».

если готово — перед реализацией:

1. **проверь готовность продуктовой спеки** (только для типа FEATURE; для BUGFIX / REFACTOR / INFRA / DOCS / DEPENDENCY этот шаг пропускается).

   - если issue ссылается на файл в `docs/product/features/` — прочитай его.
   - если issue не ссылается на спеку — поищи фичу в `docs/product/features/README.md`. Колонка `Issues` должна содержать номер этой задачи; колонка `Doc` укажет путь к спеке.
   - если спеки нет ни там, ни там — **остановись**. Не начинай реализацию. Предложи пользователю сначала проработать спеку (создать файл в `docs/product/features/` и завести строку в индексе). Объясни, что без спеки нет источника истины по acceptance criteria и out of scope, и риск уйти не туда — высокий.
   - если спека найдена — **прочитай её внимательно** и оцени:
     - **заполнена ли она достаточно** для старта реализации, или это `(stub)` с заглушками. Stub — основание остановиться и предложить дописать спеку до начала работы.
     - **какие open questions блокируют старт**, а какие можно оставить на потом. Блокирующие — те, без ответа на которые нельзя написать код или нельзя проверить acceptance. Откладываемые — те, которые касаются деталей будущих этапов или edge cases, не влияющих на основной поток.
     - **есть ли в спеке указания на реализации той же фичи на других платформах** (типичный случай: «#7 (Android); iOS, Desktop _tbd_»). Если есть:
       - посмотри, можно ли взять одну из готовых реализаций как образец (стиль, структура слоёв, тестовый паттерн).
       - заметь, что после выполнения текущей задачи может понадобиться **дописать** в спеку или в смежные tbd-задачи: что готово в common-части и от чего теперь можно отталкиваться. Это часть результата задачи, не отдельный этап.

   только после того, как спека готова и понята, переходи к шагу 2.

2. **верифицируй root cause (только для типа BUGFIX).**

   Если в issue есть раздел «Гипотезы о причинах» / «Возможные причины» / список candidate-объяснений — это **непроверенные** догадки автора issue, не факт. До написания PR обязательно подтверди реальный root cause:

   - воспроизведи баг локально (`/smoke-test` или ручной сценарий из «Воспроизведение»);
   - проверь каждую гипотезу через минимальный эксперимент — логи, `tcpdump`/`logcat`, дебаггер, lsof, sysadmin-инструменты;
   - зафиксируй подтверждённую причину **комментарием в issue** до начала кодинга, чтобы у ревьюера и у тебя самого был общий контекст;
   - если ни одна из гипотез не подтверждается — **остановись**, отчитайся пользователю, обсуди дальнейшие шаги. Не пиши код «по первой гипотезе».

   Это критичный шаг: если взять непроверенную гипотезу как факт, можно написать корректный с виду фикс, который не решает реальную проблему — а понять это получится только на стадии manual verification, потеряв несколько сессий работы.

   Для FEATURE / REFACTOR / INFRA / DOCS / DEPENDENCY этот шаг пропускается.

3. **подгрузи релевантные инженерные гайды.** В `docs/engineering/` лежат правила, которые легко нарушить молча. Подгружай только те, что реально касаются задачи:

   - **всегда, если пишешь код:** [`dependency-injection.md`](../../docs/engineering/dependency-injection.md) — чек-лист «подходит ли мой код».
   - **новые компоненты / слои / выделение в модуль:** [`architecture-principles.md`](../../docs/engineering/architecture-principles.md), [`modules.md`](../../docs/engineering/modules.md).
   - **UI:** [`presentation-layer.md`](../../docs/engineering/presentation-layer.md).
   - **новые тесты:** [`testing.md`](../../docs/engineering/testing.md).

4. **составь план реализации и стратегию валидации.** Явно отметь, если что-то в технических деталях issue вызывает сомнение или конфликтует с подгруженными гайдами — не переделывай молча, а покажи альтернативу.

   Если план добавляет новую библиотеку или мажорный апгрейд — до кодинга проверь её статус (последний релиз, deprecation от AndroidX/Apple/Kotlin, альтернативы). Verdict в тело PR разделом `## Dependency check`:
   ```
   ## Dependency check
   - foo:1.2.3 — DEPRECATED, беру альтернативу X
   - bar:4.5.6 — current
   ```

5. дождись ОК от пользователя, потом реализуй по гайду в `CLAUDE.md`.

6. **self-check реализации против гайдов.** После того как код написан и тесты зелёные, но **до запроса review / коммита**, пройди по подгруженным в шаге 3 файлам и проверь, что **фактически получилось** в diff:

   - какие правила из гайдов задеваются изменением (DI checklist, layering, presentation, testing — по конкретным пунктам);
   - реализация им соответствует — или есть **осознанные отклонения** с обоснованием.

   Цель — поймать тихое расхождение между планом и кодом до того, как его поймает ревьюер. Если расхождение есть и не обосновано — почини до запроса review. Чек на уровне плана не заменяет этот: план и реализация легко расходятся по дороге.

7. **runtime self-check (smoke).** До запроса ревью прогоняй релевантные блоки `/smoke-test` — задача исполнителя, не ревьюера. Ревьюер только проверяет наличие verdict'а в теле PR.

   **a. Сначала — расширь smoke, если нужно.** PR ввёл новую критическую функциональность, которой нет в `/smoke-test`? Критическая = точка отказа на старте, happy-path фичи, cross-platform reusable UI, новый внешний интерфейс. Если да — допиши блок в `.claude/skills/smoke-test/SKILL.md` в этом же PR. **Не раздувай:** помни, что смоук прогоняется часто, а тесты в нем дорогие по времени.

   **b. Затем прогоняй релевантные блоки и записывай verdict** в тело PR:
   
   🟡/🔴 — не отправляй в ревью до резолва.
