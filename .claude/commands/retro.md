Проведи ретроспективу по задаче <issue number> (и связанному PR, если есть).

Цель — не отчёт ради отчёта, а конкретные улучшения: в командах, скиллах, документации, процессе. Каждый вывод должен заканчиваться действием.

---

## Шаг 1 — Сбор фактов

Собери контекст:

```bash
gh issue view <N> --json title,body,comments
gh pr view <PR> --json title,body,commits,comments,reviews  # если известен
git log --oneline <merge-commit> -1  # если уже смержен
```

Прочитай всю историю: issue, комментарии, review, переписку в PR.

---

## Шаг 2 — Анализ процесса

Ответь на каждый вопрос — коротко и честно:

**Стандартность хода:**
- Задача была выполнена с первого подхода, или были откаты / переосмысления?
- Агент принимал решения, которые потом пришлось отменять?
- Потребовался повторный ресёрч по теме, которая должна была быть известна из документации?
- Пользователь несколько раз перенаправлял агента?

**Информационные пробелы:**
- Чего не хватало в issue, чтобы взять задачу без уточнений?
- Была ли нужная информация в проекте, но агент её не нашёл или не прочитал?
- Что стоило прояснить до начала реализации, но не было прояснено?

---

## Шаг 3 — Анализ бага (только если задача — багфикс)

Если задача была исправлением бага:

1. **Как баг попал в main?**
   - Отсутствие теста на конкретный сценарий?
   - Неправильное допущение в коде?
   - Граничный случай, не описанный в issue?
   - Ошибка ревью?

2. **Где нужна дополнительная защита?**
   - Тест, который ловил бы этот баг при регрессии
   - Валидация, которой не хватало
   - Явное ограничение в документации (CLAUDE.md, feature-спек), которое предотвратило бы ошибку

3. Если защита простая — добавь сразу. Если требует отдельной задачи — создай issue.

---

## Шаг 4 — Что оптимизировать

На основе анализа выше определи: что конкретно мешало работе?

Категории для улучшений:

| Категория | Когда трогать |
|-----------|--------------|
| `.claude/commands/*.md` | Команда давала нечёткие инструкции, агент делал не то |
| `.claude/skills/` | Скилл не покрывал нужный сценарий |
| `CLAUDE.md` | Агент не знал о конвенции/процессе/структуре проекта |
| `docs/product/` | Не хватало продуктового контекста для принятия решений |
| `.claude/skills/github-issue-author` | Issue содержал недостаточно деталей для реализации |
| `code-review.md` | Ревью пропустило то, что не должно было пропустить |

---

## Шаг 5 — Формулировка действий (без применения)

На основе анализа составь список предлагаемых изменений. **Не применяй их сразу** — сначала нужен явный апрув.

Для каждого улучшения укажи:
- Что именно изменить (файл, раздел)
- Почему это нужно (связь с конкретным инцидентом из истории задачи)
- Размер: «маленькое» (правка на месте) или «задача» (отдельный issue)

Выведи список и явно спроси:

> Подтверждаешь эти изменения? Если нет — скажи, что скорректировать.

**Не переходи к шагу 6 без явного «да» или «ок» от пользователя.**

---

## Шаг 6 — Применение (только после апрува)

Для каждого подтверждённого улучшения:

**Если изменение маленькое** (правка в документе, уточнение в команде) — сделай прямо сейчас и покажи diff.

**Если изменение требует отдельной задачи** — создай issue через скилл `github-issue-author`. Название должно читаться как полезный инкремент к рабочему процессу, например:
- «Добавить проверку X в code-review.md»
- «Уточнить scope команды work-on-issue для случая Y»

**Итог ретро** — выведи списком:
- ✅ Сделано сразу: [что именно]
- 📋 Запланировано: [issue #N — что]
- 💡 Наблюдение без действия: [если есть — почему без действия]
