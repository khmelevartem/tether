# Ручной DI в Kotlin Multiplatform: composition root вместо фреймворка

Kotlin Multiplatform-приложение можно собрать без DI-фреймворка. Без рефлексии, без кодогенерации, без аннотаций и DSL. Внедрение зависимостей сводится к одной идее: есть единственное место, где создаются общие компоненты, — composition root, — а все остальные классы получают готовые зависимости в конструктор.

Ключевая идея специфична для KMP и структурна: иерархия контейнеров повторяет иерархию сорс-сетов. Место каждого компонента определяется тем, какой API виден его сорс-сету, — структура сама отвечает на вопрос «где это создавать». Этого приёма я не встречал в статьях про ручной DI: его либо подают как ступень перед фреймворком, либо описывают вне контекста KMP.

Это не отказ от инструмента из принципа. Фреймворк решает реальные проблемы, и в большом проекте он эти проблемы окупает. Но он же добавляет компилятор-плагин или KSP, свой жизненный цикл сборки, свои правила и свою кривую обучения. Пока проблем, которые он решает, ещё нет, он остаётся аппаратом тяжелее задачи. В этой статье я показываю, как устроен ручной DI в [Tether](https://github.com/khmelevartem/tether) — KMP-приложении для передачи файлов между устройствами (Android, iOS, Desktop), — и где проходит честная граница, за которой фреймворк наконец оправдан.

Код в примерах — синтетический: имена классов обобщены, чтобы показать форму паттерна, а не конкретную реализацию. Сами паттерны взяты из боевого кода.

## Предпосылки

Чтобы паттерн имел смысл, нужны три вещи.

- Проект на Kotlin Multiplatform с иерархией сорс-сетов: общий код в `commonMain`, платформенный — в `androidMain`, `iosMain`, `jvmMain` и так далее.
- В приложении есть место, которое хранит созданные зависимости и владеет их жизненным циклом.
- Зависимости по умолчанию передаются в конструкторы, а не достаются из глобального состояния.

Дальше я раскрываю каждую из этих вещей: сначала на уровне приложения, потом — как тот же подход масштабируется на отдельные KMP-библиотеки.

## Главная идея: composition root

Composition root — единственное место, где приложение собирает граф зависимостей. Я называю его контейнером. Контейнер создаёт общие компоненты по одному разу и раздаёт их всем, кому они нужны. Никто, кроме контейнера, не вызывает конструктор общего компонента.

```kotlin
class AppContainer {
    val httpClient: HttpClient by lazy { HttpClient() }
    val messageRepository: MessageRepository by lazy { MessageRepository(httpClient) }
    val syncService: SyncService by lazy { SyncService(messageRepository) }
}
```

Каждый компонент получает свои зависимости в конструктор. Контейнер знает порядок сборки и владеет синглтонами. Класс `SyncService` не знает, откуда взялся `MessageRepository`, — он его принимает. Это и есть внедрение зависимостей: не «фреймворк подставил», а «вызывающий передал».

Главное преимущество видно сразу в тестах. Раз `SyncService` принимает `MessageRepository` в конструктор, тест передаёт туда фейк — без моков, без рефлексии, без подмены глобалов.

### Это DI, а не service locator

Ручному DI часто возражают: на практике он вырождается в service locator — глобальный реестр, из которого классы достают зависимости сами. Возражение бьёт мимо. Разница в направлении управления: при service locator класс знает про реестр и тянет зависимости из него; при инъекции через конструктор класс не знает ни про какой контейнер — зависимости в него передаёт composition root. Контейнер здесь не реестр для чтения, а место сборки. Эту границу подробно разобрал [Мартин Фаулер](https://martinfowler.com/articles/injection.html); она же отделяет настоящий DI от подделки.

Единственное место, где класс всё-таки обращается к контейнеру сам, — Android-компоненты с пустыми конструкторами. Это явная, огороженная уступка, а не общий способ доставать зависимости; разбираю ниже.

## Иерархия контейнеров повторяет иерархию сорс-сетов

В KMP-приложении не один контейнер, а дерево. И это дерево повторяет дерево сорс-сетов. Каждый слой добавляет только то, что его сорс-сет вообще способен увидеть.

![Иерархия контейнеров повторяет иерархию сорс-сетов](manual-di-source-set-hierarchy.png)

```
AppContainer            (commonMain)
├── JvmAppContainer     (jvmMain)
│   ├── AndroidAppContainer  (androidMain)
│   └── DesktopAppContainer  (desktopMain)
└── AppleAppContainer   (appleMain)
    └── IosAppContainer      (iosMain)
```

`AppContainer` в `commonMain` собирает всё, что выражается общим кодом. `AndroidAppContainer` в `androidMain` добавляет компоненты, которым нужен `Context` или другой Android-API. `IosAppContainer` — то, что требует Apple-фреймворков. Платформенный лист наследует общий контейнер и доопределяет недостающее.

Граница проходит ровно по видимости API. Если компонент собирается из общих абстракций — он живёт в общем контейнере. Если ему нужен платформенный тип — он спускается в платформенный лист. Дерево контейнеров отвечает на вопрос «где создавать этот компонент» механически: там, где впервые становится виден нужный API.

## Конфигурация: вход в контейнер

Контейнеру нужны значения, которые знает только точка входа: порт сервера, каталог загрузок, ссылка на Android `Application`. Эти значения собираются в отдельный объект конфигурации, и его иерархия повторяет иерархию контейнеров.

```kotlin
// commonMain
interface AppConfig {
    val downloadsDir: String
    val port: Int
}

// androidMain
interface AndroidAppConfig : AppConfig {
    val application: Application
}
```

Контейнер принимает конфигурацию в конструктор. `AppContainer` в `commonMain` — без аргументов; промежуточные контейнеры берут свой подтип `AppConfig`; листья передают конкретную конфигурацию наверх.

Конфигурация — это вход. Контейнер — это то, что из входа собирается. Разделение даёт ровно одну точку, где приложение задаёт параметры, и отдельную точку, где из них строится граф.

Конкретные реализации конфигурации — именованные классы в своих файлах, не анонимные `object : AppConfig { … }`. Анонимный объект на месте вызова провоцирует расхождение между точками сборки: два места создают «почти такую же» конфигурацию, и они тихо расходятся. Именованный класс — одна точка правды.

## Точки входа платформ

Каждая платформа строит свой лист контейнера в собственной точке входа и раздаёт компоненты вниз.

- На **Android** контейнер собирается в подклассе `Application` и живёт столько же, сколько процесс.
- На **iOS** контейнер собирается в точке входа UI — но снаружи `Composable`-лямбды, чтобы composable не превратился в composition root (об этом ниже).
- На **Desktop** точек входа может быть несколько: например, отдельный запуск GUI и отдельный — CLI. Каждая собирает свой лист контейнера, и на classpath каждой компиляции попадает только то, что ей нужно.

Точка входа знает жизненный цикл. Всё остальное получает уже живые компоненты.

## Паттерн Provider для Android

С Android есть отдельная сложность. Его системные компоненты — `Activity`, `Service`, `BroadcastReceiver` — создаёт фреймворк, и у них должны быть пустые конструкторы. Передать им контейнер через конструктор, как обычному классу, нельзя.

Решение, которое ложится на эту ситуацию:

1. Подкласс `Application` реализует интерфейс-провайдер и владеет контейнером.
2. Системные компоненты достают контейнер через приведение: `(application as AppContainerProvider).container`.

![Паттерн Provider для Android-компонентов](manual-di-android-provider.png)

```kotlin
interface AppContainerProvider {
    val container: AppContainer
}

class MyApp : Application(), AppContainerProvider {
    override val container: AppContainer by lazy { AndroidAppContainer(/* config */) }
}

class MyService : Service() {
    private val container by lazy { (application as AppContainerProvider).container }
}
```

Это не service locator, хотя выглядит похоже. Разница в дисциплине: интерфейс-провайдер реализует ровно один тип (боевой `Application` и тестовый — в тестах), а доступ через него имеют только классы, которыми управляет Android-фреймворк. Обычные Kotlin-классы по-прежнему получают зависимости в конструктор. Статический доступ — это явная неустранимая уступка пустым конструкторам, а не способ доставать что угодно откуда угодно.

Сам приём — официальная рекомендация Android для ручного DI ([Manual dependency injection](https://developer.android.com/training/dependency-injection/manual)). Правда, в документации он подан как ступень перед Hilt; здесь он остаётся самостоятельным решением ровно до тех пор, пока не сработают триггеры из последнего раздела.

## Принципы: подходит ли мой код

Composition root работает, пока код вокруг него соблюдает несколько правил. Это и чек-лист для нового кода, и определение того, что вообще считается зависимостью.

**Только инъекция через конструктор — не создавайте коллабораторов сами.** Конструктор класса — это его честный список зависимостей. Всё, что класс достаёт из глобалов или создаёт внутри, в этом списке невидимо.

```kotlin
// плохо: класс владеет своим коллаборатором, его не подменить в тесте
class SomeService {
    private val repo = SomeRepository()
}

// хорошо: зависимость явная
class SomeService(private val repo: SomeRepository)
```

Сюда же — про `nullable`-зависимость со значением `= null` по умолчанию. Если боевая сборка всегда передаёт коллаборатора, а в сигнатуре он опциональный, то вызов, который его забыл, тихо отключит фичу без ошибки компиляции. Делайте такую зависимость обязательной. Значение по умолчанию `null` оставляйте только для по-настоящему опциональной зависимости — и тогда тестируйте ветку с `null`.

**Платформенный контекст — это зависимость, а не глобал.** Точка входа уже держит `Context` приложения. Передайте его в конструктор, а не доставайте из статического поля.

```kotlin
// плохо
actual class SomeService {
    private val manager = GlobalApp.context.getSystemService(/* … */)
}

// хорошо
actual class SomeService(context: PlatformContext) {
    private val manager = context.getSystemService(/* … */)
}
```

**Один синглтон — один владелец.** Если компонент задуман как синглтон, он создаётся ровно один раз — в composition root. Не в `object`, не лениво из глубины другого компонента. Жизненный цикл знает только корень; везде ещё вы получаете то, что уже живёт.

**Не создавайте зависимости внутри composable.** Composable, который сам вызывает конструктор сервиса, — это composition root не на своём месте.

```kotlin
// плохо: новый экземпляр на каждую рекомпозицию, утечка
@Composable
fun SomeScreen() {
    val service = SomeService(SomeRepository())
    DisposableEffect(Unit) {
        service.start()
        onDispose { service.stop() }
    }
}
```

`DisposableEffect(Unit)` отработает один раз и захватит экземпляр из первой композиции. На каждой следующей рекомпозиции создаётся новый `SomeService`, который тут же выбрасывается, — его не запускают и не останавливают. Даже `remember` тут лечит утечку, но не главную ошибку: composable владеет жизненным циклом синглтона, а не должен. Правильная форма — собрать контейнер в точке входа и передать готовый компонент внутрь.

**Не вводите интерфейс ради одной реализации.** Интерфейс зарабатывает право на существование, когда есть фейк для тестов или вторая боевая реализация (например, разные файловые серверы на JVM и iOS). Интерфейс `SomeRepository` с единственным `SomeRepositoryImpl` добавляет шум, а не безопасность. Это сознательное расхождение с карго-культом «Чистой архитектуры», где интерфейс заводят под каждый класс на всякий случай.

**Для тестовых швов — фейки, а не интерфейсы-обёртки.** Когда класс всё-таки надо протестировать, пишите фейк руками, а не вводите интерфейс только ради мока. Мок-фреймворк навязывает слой косвенности, который протекает в боевой код. Если фейк тяжело написать, потому что компонент слишком связан с коллабораторами, чините компонент.

**Контейнер хранит именованные компоненты, а не голые данные.** Поле контейнера — это объект, который чем-то владеет или управляет: хранилище, сервер, клиент, скоуп, фабрика. Не строка, не число, не порт, не тег. Значения вроде идентификатора, алиаса или порта принадлежат тому компоненту, который ими владеет; потребитель получает компонент и спрашивает значение в тот момент, когда оно нужно, — в том числе после асинхронной границы, если значение известно только после I/O. Голые данные на контейнере заставляют материализовать их в момент сборки, прячут, кто за них отвечает, и превращают граф зависимостей в мешок свойств.

**Никаких молча бросающих общих дефолтов.** Когда поле контейнера требует платформенной реализации, общий контракт говорит об этом явно: поле `abstract` на общем контейнере — тогда каждый платформенный лист обязан его доопределить, иначе не скомпилируется. Конкретный общий дефолт, который бросает исключение и работает только потому, что одна платформа его случайно переопределила, — худший вариант: он компилируется, проходит тесты на фейках и падает в рантайме на той платформе, что забыла переопределить.

## Тестируемость

Контейнер — это ещё и шов, через который тесты подставляют фейки. Чтобы это работало, поля контейнера объявляются как `open val`: переопределение и есть механизм подмены. Никаких сеттеров, никакого `lateinit var`.

```kotlin
class FakeContainer : AppContainer() {
    override val httpClient = FakeHttpClient()
    override val messageRepository = FakeMessageRepository()
}
```

Тест собирает фейковый контейнер наследованием и переопределяет нужные поля. Компоненты, которые берут зависимости в конструктор, тестируются напрямую — контейнер им не нужен вовсе; он существует ради боевой сборки.

Для тестов Android-компонентов под Robolectric нужен `Application`, который реализует интерфейс-провайдер. Либо берётся боевой `Application`, либо определяется тестовый с фейковым контейнером — и каждый тест получает свежий экземпляр, ничего не оседает в статике.

## Как это масштабируется на библиотеки

Пока приложение — один модуль, composition root остаётся плоским. Но тот же подход растёт до отдельных KMP-библиотек, и там добавляется ещё один разрез: что библиотека показывает наружу, а что прячет.

### Разделение на Api и Impl

Библиотека делится на два модуля. Модуль **Api** содержит только интерфейсы и модели для внешнего использования. Модуль **Impl** зависит от Api и содержит все реализации.

Единственный модуль приложения, который зависит от **Impl**, — тот, где собирается DI. Остальные модули приложения и другие библиотеки зависят только от **Api**. Единственный класс из **Impl**, к которому обращается потребитель, — точка входа в библиотеку.

![Подключение Api и Impl](manual-di-api-impl.png)

Зачем разрез: он строго обозначает публичное API библиотеки и за счёт этого утоньшает интеграционный слой. Потребитель видит ровно то, что библиотека пообещала, и не может случайно опереться на реализацию.

### Публичный и внутренний контейнеры

У библиотеки контейнер раздваивается по видимости.

- **LibPublicContainer** — публичное API (фасад) библиотеки. В нём лежат все зависимости, которые библиотека отдаёт внешним потребителям.
- **LibInternalContainer** — наследник публичного, добавляющий зависимости для внутреннего использования. Внешним потребителям они не видны.

Приложение хранит созданный контейнер и пользуется им по публичному интерфейсу. Внутренние классы самой библиотеки — по расширенному.

![Публичный и внутренний контейнеры](manual-di-public-internal.png)

```kotlin
// модуль Api
interface LibPublicContainer {
    val someRepository: SomeRepository
}

// модуль Impl
interface LibInternalContainer : LibPublicContainer {
    val someInternalService: SomeInternalService
}
```

### Точка входа в библиотеку

У библиотеки одна точка входа — `LibModule`. Его единственная ответственность — создать контейнер. Больше он не делает ничего.

```kotlin
// модуль Api
interface LibModule {
    fun create(config: LibConfigContainer): LibPublicContainer
}
```

Приложение реализует интерфейс конфигурации `LibConfigContainer` и отдаёт его в `create`. Метод возвращает контейнер по публичному интерфейсу; внутри библиотека знает, что это полный контейнер с внутренней частью.

```kotlin
class App {
    val lib: LibPublicContainer by lazy {
        LibModuleImpl.create(AndroidLibConfig(application = this))
    }
}
```

Дальше готовый контейнер достаточно прокинуть в конструкторы потребителей:

```kotlin
val someInteractor: SomeInteractor by lazy {
    SomeInteractor(repository = lib.someRepository)
}
```

### Статический доступ изнутри библиотеки

Иногда внутренним классам библиотеки нужно достать контейнер статически, а не через конструктор, — та же история, что с Android-компонентами. Тогда библиотека объявляет интерфейс-провайдер, а приложение его реализует.

```kotlin
// в библиотеке (модуль Api)
interface LibProvider {
    val lib: LibPublicContainer
}

// в приложении
class App : Application(), LibProvider {
    override val lib: LibPublicContainer by lazy {
        LibModuleImpl.create(AndroidLibConfig(application = this))
    }
}

// внутри библиотеки
class LibActivity : Activity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val internal = (application as? LibProvider)?.lib as? LibInternalContainer
        internal?.someInternalService?.start()
    }
}
```

### Платформенный контейнер

Если у библиотеки много платформенных зависимостей, удобно вынести их в отдельный `LibPlatformContainer` и собирать контейнер композицией, а не наследованием. Это необязательный элемент: при малом числе платформенных зависимостей их объявляют прямо в `LibInternalContainer` и реализуют в его платформенных листах.

### Порядок инициализации

Сборка контейнера библиотеки идёт по шагам.

![Порядок инициализации DI библиотеки](manual-di-init-order.png)

1. Приложение реализует интерфейс конфигурации `LibConfigContainer` и отдаёт его в `LibModule.create`.
2. Библиотека создаёт платформенную реализацию `LibPlatformContainer` — свою внутреннюю сущность.
3. Из конфигурации и платформенного контейнера библиотека собирает полный контейнер, реализующий и публичный, и внутренний интерфейсы.
4. Приложение сохраняет контейнер и отдаёт его наружу через `LibProvider`.
5. Приложение пользуется контейнером по публичному интерфейсу; классы внутри библиотеки — по внутреннему.

Дисциплина та же, что в приложении. Модуль не занимается ничем, кроме создания контейнера. Контейнеры не реализуют никаких посторонних интерфейсов: конфигурация и платформенный контейнер, попавшие в конструктор, — это детали реализации, а не часть публичного фасада.

## Когда фреймворк наконец оправдан

Ручной DI окупается до определённого масштаба. Дальше начинает болеть, и тогда переход на фреймворк — это осознанное решение, а не поражение.

Граница проходит по конкретным триггерам. Я перехожу на DI-фреймворк, когда срабатывает хоть один:

- выделяется третий Gradle-модуль, и проводка зависимостей через границы модулей в контейнере становится утомительной;
- я впервые забываю зарегистрировать зависимость и отгружаю краш на платформу;
- лист контейнера разрастается за разумный предел или начинает ветвиться по флейворам сборки.

Пока ни один не сработал, компилятор-плагин — это больше аппарата, чем заслуживает задача.

Важно, что иерархия контейнеров и паттерн провайдера ложатся на форму фреймворка почти один в один. Контейнер становится графом зависимостей, платформенные подклассы — платформенными вкладами в граф, интерфейсы конфигурации — провайдерами значений. Тесты, которые переопределяли `open val`, становятся тестовыми графами с переопределённым связыванием. Структуру перетряхивать не приходится — поэтому отложить переход дёшево.

Выбор конкретного фреймворка — отдельный разговор, и критерии для KMP свои. Для проекта на Kotlin Multiplatform я смотрю в первую очередь на:

- **поддержку всех целевых платформ** — iOS-таргеты, JVM, Android должны поддерживаться явно;
- **проверку графа на этапе компиляции** — забытая зависимость должна валить сборку, а не падать в рантайме на той платформе, что тестировалась последней;
- **скорость сборки** — компилятор-плагин обычно быстрее KSP;
- **эргономику в многомодульном проекте** — как фреймворк связывает вклады из разных модулей.

Решения с рантайм-резолвингом для KMP проигрывают по первому же критерию: в приложении, где каждый таргет тестируется отдельно, «забыл зарегистрировать» превращается в краш на устройстве вместо ошибки компиляции.

По этим критериям мой выбор на сегодня — [Metro](https://github.com/ZacSweers/metro): он KMP-first, проверяет граф на компиляции и работает как компилятор-плагин, а не через KSP. Koin отпадает по второму критерию — рантайм-резолвинг. kotlin-inject хорош технически, но на KSP, и потому проигрывает в скорости сборки. Dagger и Hilt — не KMP вовсе. Но Metro здесь — пункт назначения, а не отправная точка: пока ни один триггер не сработал, он остаётся лишним аппаратом. Важно ровно одно — что момент перехода виден заранее и стоит дёшево.

## Преимущества подхода

- **Никакого аппарата раньше времени.** Нет плагина, кодогенерации, рантайм-резолвинга. Граф зависимостей — это обычный Kotlin-код, который читается и отлаживается как любой другой.
- **Честные конструкторы.** Сигнатура класса — это его полный список зависимостей. Ничего не приходит из невидимого глобала.
- **Структура отвечает на вопрос «где создавать».** Дерево контейнеров повторяет дерево сорс-сетов, и место компонента определяется механически — там, где впервые виден нужный API.
- **Тонкий интеграционный слой для библиотек.** Разделение на Api и Impl строго обозначает публичную поверхность.
- **Дешёвый переход на фреймворк.** Когда триггеры сработают, форма уже совпадает с формой графа — переезжать без структурной перетряски.

Композиция вместо магии. Пока проект её перерастёт, у вас будет ровно столько DI, сколько нужно, — и ни строкой больше.
