# Ручной DI в Kotlin Multiplatform: composition root вместо фреймворка

Kotlin Multiplatform-приложение можно собрать без DI-фреймворка. Без рефлексии, без кодогенерации, без аннотаций и DSL. Внедрение зависимостей сводится к одной идее: есть единственное место, где создаются общие компоненты, — composition root, — а все остальные классы получают готовые зависимости в конструктор.

Сам composition root — не изобретение и не что-то про KMP. Термин ввёл Марк Симан (Mark Seemann), автор книги «Dependency Injection», и описал его как единственную точку, где собирается весь граф объектов приложения ([ploeh.dk](https://blog.ploeh.dk/2011/07/28/CompositionRoot/)). Паттерн одинаково работает в .NET, на бэкенде, в Python — в любом модульном приложении, которое собирает зависимости в одной точке входа. KMP добавляет к нему ровно одну ось: иерархию сорс-сетов. О ней дальше — иерархия контейнеров повторяет иерархию сорс-сетов, и место каждого компонента определяется тем, какой API виден его сорс-сету.

Зачем вообще ручной DI, если есть зрелые фреймворки? Главная причина — наглядность. Граф зависимостей здесь — обычный код: видно, что и где создаётся, любую связь можно пройти через «go to definition» в IDE. Никакой магии, никаких объектов «из воздуха» — то, что во фреймворке скрыто за аннотациями и кодогенерацией, лежит открытым текстом. Из наглядности вытекает остальное: нулевая стоимость входа (нет плагина, настройки сборки, версионных конфликтов), отладка обычным дебаггером по неперегенерированному коду, низкий порог для нового человека в команде — учить нечего, читается как любой Kotlin.

Это не отказ от инструмента из принципа. Фреймворк решает реальные проблемы, и на большом проекте он окупается. Но он же добавляет компилятор-плагин или KSP, свой жизненный цикл сборки, свои правила и свою кривую обучения. Пока проблем, которые он решает, ещё нет, он остаётся аппаратом тяжелее задачи. В этой статье я показываю, как устроен ручной DI в [Tether](https://github.com/khmelevartem/tether) — KMP-приложении для передачи файлов между устройствами (Android, iOS, Desktop), — и где проходит граница, за которой фреймворк начинает себя окупать.

Код в примерах — синтетический: имена классов обобщены, чтобы показать форму паттерна, а не конкретную реализацию. Сами паттерны взяты из боевого кода.

## Предпосылки

Чтобы паттерн имел смысл, нужны три вещи.

- Проект на Kotlin Multiplatform с иерархией сорс-сетов: общий код в `commonMain`, платформенный — в `androidMain`, `iosMain`, `jvmMain` и так далее.
- В приложении есть место, которое хранит созданные зависимости и владеет их жизненным циклом.
- Зависимости по умолчанию передаются в конструкторы, а не достаются из глобального состояния.

Дальше я раскрываю каждую из этих вещей: сначала на уровне приложения, потом — как тот же подход масштабируется на отдельные KMP-библиотеки.

## Главная идея: composition root

Composition root — единственное место, где приложение собирает граф зависимостей. Я называю его контейнером. Контейнер создаёт общие компоненты по одному разу и раздаёт их всем, кому они нужны. Никто, кроме контейнера, не вызывает конструктор общего компонента.

```kotlin
class AppContainer {
    val httpClient: HttpClient by lazy { HttpClient() }
    val messageRepository: MessageRepository by lazy { MessageRepository(httpClient) }
    val syncEngine: SyncEngine by lazy { SyncEngine(messageRepository) }
}
```

Поля здесь ленивые, но это деталь: режим создания задаёт контейнер. Где ленивость не нужна — компонент собирается сразу; где `by lazy` мешает синхронизацией — берётся `LazyThreadSafetyMode.NONE`. Важно одно: порядок и момент создания решает контейнер, а не случайность обращения.

Каждый компонент получает свои зависимости в конструктор. Класс `SyncEngine` не знает, откуда взялся `MessageRepository`, — он его принимает. Это и есть внедрение зависимостей: зависимость передаёт вызывающий.

Главное преимущество видно сразу в тестах. Раз `SyncEngine` принимает `MessageRepository` в конструктор, тест передаёт туда фейк — без моков, без рефлексии, без подмены глобалов.

### Это DI, а не service locator

Ручному DI часто возражают: на практике он вырождается в service locator — глобальный реестр, из которого классы достают зависимости сами. Для конструкторной инъекции это возражение не работает. Разница в направлении управления: при service locator класс знает про реестр и тянет зависимости из него; при инъекции через конструктор класс не знает ни про какой контейнер — зависимости в него передаёт composition root. Контейнер здесь — место сборки, и классы из него не читают. Эту границу подробно разобрал [Мартин Фаулер](https://martinfowler.com/articles/injection.html).

Одно исключение есть, и прятать его я не буду: Android-компоненты с пустыми конструкторами вынуждены доставать контейнер сами. Это локальный service locator на границе с чужим фреймворком — называю вещи своими именами в разделе про Provider.

## Иерархия контейнеров повторяет иерархию сорс-сетов

В KMP-приложении контейнеров целое дерево. Оно повторяет дерево сорс-сетов. Каждый слой добавляет только то, что его сорс-сет способен увидеть.

![Иерархия контейнеров повторяет иерархию сорс-сетов](manual-di-source-set-hierarchy.png)

```
AppContainer            (commonMain)
├── JvmAppContainer     (jvmMain)
│   ├── AndroidAppContainer  (androidMain)
│   └── DesktopAppContainer  (desktopMain)
└── AppleAppContainer   (appleMain)
    └── IosAppContainer      (iosMain)
```

`AppContainer` в `commonMain` собирает всё, что выражается общим кодом. `AndroidAppContainer` в `androidMain` добавляет компоненты, которым нужен `Context` или другой Android-API. `IosAppContainer` — то, что требует Apple-фреймворков. Платформенный лист (так я называю конечный узел дерева — `leaf`) наследует общий контейнер и доопределяет недостающее.

Граница проходит по видимости API. Если компонент собирается из общих абстракций — он живёт в общем контейнере. Если ему нужен платформенный тип — он спускается в платформенный лист. Компонент создаётся там, где впервые становится виден нужный API.

## Конфигурация: вход в контейнер

Контейнеру нужны значения, которые знает только точка входа: порт сервера, каталог загрузок, ссылка на Android `Application`. Эти значения собираются в отдельный объект конфигурации, и его иерархия повторяет иерархию контейнеров.

```kotlin
// commonMain
interface AppConfig {
    val downloadsDir: String
    val port: Int
}

// androidMain
interface AndroidAppConfig : AppConfig {
    val application: Application
}
```

Контейнер принимает конфигурацию в конструктор. `AppContainer` в `commonMain` — без аргументов; промежуточные контейнеры берут свой подтип `AppConfig`; листья передают конкретную конфигурацию наверх.

Конфигурация — это вход. Контейнер — это то, что из входа собирается. Разделение даёт ровно одну точку, где приложение задаёт параметры, и отдельную точку, где из них строится граф.

Конкретные реализации конфигурации — именованные классы в своих файлах, не анонимные `object : AppConfig { … }`. Анонимный объект на месте вызова провоцирует расхождение между точками сборки: два места создают «почти такую же» конфигурацию, и они тихо расходятся. Именованный класс — одна точка правды.

## Точки входа платформ

Каждая платформа строит свой лист контейнера в собственной точке входа и раздаёт компоненты вниз.

- На **Android** контейнер собирается в подклассе `Application` и живёт столько же, сколько процесс.
- На **iOS** контейнер собирается в точке входа UI — снаружи функции, которая запускает интерфейс, чтобы эта функция не превратилась в ещё один composition root.
- На **Desktop** точек входа может быть несколько: например, отдельный запуск GUI и отдельный — CLI. Каждая собирает свой лист контейнера, и на classpath каждой компиляции попадает только то, что ей нужно.

Точка входа знает жизненный цикл. Всё остальное получает уже живые компоненты.

## Паттерн Provider для Android

С Android есть отдельная сложность. Его системные компоненты — `Activity`, `Service`, `BroadcastReceiver` — создаёт фреймворк, и у них должны быть пустые конструкторы. Передать им контейнер через конструктор, как обычному классу, нельзя.

Решение, которое ложится на эту ситуацию:

1. Подкласс `Application` реализует интерфейс-провайдер и владеет контейнером.
2. Системные компоненты достают контейнер через приведение: `(application as AppContainerProvider).container`.

![Паттерн Provider для Android-компонентов](manual-di-android-provider.png)

```kotlin
interface AppContainerProvider {
    val container: AppContainer
}

class MyApp : Application(), AppContainerProvider {
    override val container: AppContainer by lazy { AndroidAppContainer(/* config */) }
}

class MyService : Service() {
    private val container by lazy { (application as AppContainerProvider).container }
}
```

Выглядит как service locator — и отчасти так и есть: это статический доступ к глобалу. Прятать это за терминологией я не буду. На границе с чужим фреймворком, который сам создаёт объекты и требует пустых конструкторов, у конструкторной инъекции просто нет хода. Поэтому здесь — локальный service locator, и он меньшее зло ровно потому, что огорожен: интерфейс-провайдер реализует один тип (боевой `Application`, в тестах — тестовый), доступ через него имеют только классы под управлением Android, а число таких точек конечно и всё на виду. Обычные Kotlin-классы по-прежнему получают зависимости в конструктор.

Сам приём документирован Android как способ ручного DI ([Manual dependency injection](https://developer.android.com/training/dependency-injection/manual)) — правда, там он подан как ступень перед Hilt. Здесь он остаётся самостоятельным решением ровно до тех пор, пока не сработают триггеры из раздела про фреймворк.

## Принципы ручного DI

Composition root держится на нескольких правилах. Часть из них — то, без чего ручной DI ломается. Часть — рекомендации, которые делают код чище, но саму картину сборки графа не меняют. Сначала первые.

**Только инъекция через конструктор — не создавайте коллабораторов сами.** Конструктор класса — это его честный список зависимостей. Всё, что класс достаёт из глобалов или создаёт внутри, в этом списке невидимо.

```kotlin
// плохо: класс владеет своим коллаборатором, его не подменить в тесте
class SyncEngine {
    private val repo = SomeRepository()
}

// хорошо: зависимость явная
class SyncEngine(private val repo: SomeRepository)
```

Сюда же — про `nullable`-зависимость со значением `= null` по умолчанию. Если боевая сборка всегда передаёт коллаборатора, а в сигнатуре он опциональный, то вызов, который его забыл, тихо отключит фичу без ошибки компиляции. Делайте такую зависимость обязательной. Значение по умолчанию `null` оставляйте только для по-настоящему опциональной зависимости — и тогда тестируйте ветку с `null`.

**Платформенный контекст — это зависимость, а не глобал.** Точка входа уже держит `Context` приложения. Передайте его в конструктор, а не доставайте из статического поля.

```kotlin
// плохо
actual class SyncEngine {
    private val manager = GlobalApp.context.getSystemService(/* … */)
}

// хорошо
actual class SyncEngine(context: PlatformContext) {
    private val manager = context.getSystemService(/* … */)
}
```

**Один синглтон — один владелец.** Если компонент задуман как синглтон, он создаётся ровно один раз — в composition root. Не в `object`, не лениво из глубины другого компонента. Жизненный цикл знает только корень; в остальных местах вы получаете то, что уже живёт.

**Не создавайте зависимости внутри composable.** Composable, который сам собирает сервис, — это composition root не на своём месте. Грубый случай очевиден: без `remember` на каждой рекомпозиции рождается новый экземпляр и тут же выбрасывается — утечка и мёртвый объект. Но даже аккуратный вариант с `remember` неверен:

```kotlin
@Composable
fun SomeScreen() {
    val engine = remember { SyncEngine(SomeRepository()) }
    DisposableEffect(Unit) {
        engine.start()
        onDispose { engine.stop() }
    }
}
```

`remember` убирает утечку, но не главную ошибку: composable владеет жизненным циклом синглтона, а владеть им должна точка входа. Правильная форма — собрать контейнер в точке входа и передать готовый компонент внутрь.

**Контейнер хранит именованные компоненты, а не голые данные.** Поле контейнера — это объект, который чем-то владеет или управляет: хранилище, сервер, клиент, скоуп, фабрика. Не строка, не число, не порт, не тег.

За этим стоит не вкусовщина. Любое значение неявно несёт логику — доменную или слоя данных. Положить в контейнер готовую строку `deviceId` — значит зашить решение «это значение доступно сразу, всегда и всем». Но откуда оно берётся? Возможно, его надо прочитать с диска, сгенерировать при первом запуске, дождаться после сетевого ответа. Эта логика кому-то принадлежит — компоненту, который за `deviceId` отвечает. Контейнер логикой не владеет, даже такой простой; он только собирает компоненты, которые ею владеют.

```kotlin
// плохо: контейнер владеет данными и зашивает «доступно сразу»
class AppContainer {
    val deviceId: String = readDeviceId()
}

// хорошо: контейнер собирает владельца, тот отдаёт значение, когда оно готово
class AppContainer {
    val identity: DeviceIdentity by lazy { DeviceIdentity(storage) }
}
// потребитель спрашивает identity.deviceId() в нужный момент — в том числе после I/O
```

Голые данные на контейнере заставляют материализовать их в момент сборки, прячут, кто за них отвечает, и превращают граф зависимостей в мешок свойств.

**Никаких молча бросающих общих дефолтов.** Когда поле контейнера требует платформенной реализации, общий контракт говорит об этом явно: поле `abstract` на общем контейнере — тогда каждый платформенный лист обязан его доопределить, иначе не скомпилируется. Конкретный общий дефолт, который бросает исключение и работает только потому, что одна платформа его случайно переопределила, — худший вариант: он компилируется, проходит тесты на фейках и падает в рантайме на той платформе, что забыла переопределить.

### Рекомендации, а не ядро DI

Следующие два правила я держу в проекте, но к самому DI они не относятся: картину сборки графа они не меняют, а просто берегут от лишнего кода.

**Не вводите интерфейс ради одной реализации.** Интерфейс зарабатывает право на существование, когда есть фейк для тестов или вторая боевая реализация (например, разные файловые серверы на JVM и iOS). Интерфейс `SomeRepository` с единственным `SomeRepositoryImpl` добавляет шум, а не безопасность. Это сознательный отказ от привычки заводить интерфейс под каждый класс на всякий случай.

**Для тестовых швов чаще подходит фейк, а не мок.** Когда класс надо протестировать, фейк руками обычно проще и честнее, чем мок через фреймворк: мок завязывает тест на детали вызовов и подталкивает мокать то, что дешевле подменить готовым фейком. Если фейк тяжело написать, потому что компонент слишком связан с коллабораторами, — это сигнал чинить компонент, а не мокать вокруг. Подробный разбор злоупотребления моками — [у Максима Шульги](https://www.maxshulga.ru/2013/06/mockoveruse.html).

## Тестируемость

Контейнер — это ещё и шов, через который тесты подставляют фейки. Чтобы это работало, поля контейнера объявляются как `open val` (а платформенно-обязательные — как `abstract val`): переопределение и есть механизм подмены. Никаких сеттеров, никакого `lateinit var`.

```kotlin
class FakeContainer : AppContainer() {
    override val httpClient = FakeHttpClient()
    override val messageRepository = FakeMessageRepository()
}
```

Тест собирает фейковый контейнер наследованием и переопределяет только нужные поля — не плодя класс под каждый сценарий. Компоненты, которые берут зависимости в конструктор, тестируются напрямую: контейнер им не нужен вовсе, он существует ради боевой сборки.

Для тестов Android-компонентов под Robolectric нужен `Application`, который реализует интерфейс-провайдер. Либо берётся боевой `Application`, либо определяется тестовый с фейковым контейнером — и каждый тест получает свежий экземпляр, ничего не оседает в статике.

## Границы подхода

Честно про то, чего ручной DI в таком виде не даёт.

**Это канон, а не защита.** Подход — свод принципов, а не механизм принуждения. Ничто в нём не мешает кому-то создать зависимость прямо в классе или спрятать состояние в `object`. Ровно так же ни один фреймворк не запрещает писать плохо. Разница в том, что нарушение здесь видно глазами: лишний вызов конструктора или обращение к глобалу торчат в коде и в диффе. Нужны гарантии — это уровень кастомных линтеров; без них остаётся инженерная культура команды.

**Скоупы и жизненный цикл — самое слабое место.** Все контейнеры здесь — синглтоны на весь процесс. Механизма скоупов у подхода нет: ни дочерних графов под экран, ни зависимостей, живущих ровно пока открыта фича, ни выгрузки графа из памяти. Это именно то, что зрелые фреймворки умеют, а ручной DI — нет. В Tether per-screen жизненный цикл вынесен из DI в слой навигации: компоненты экрана получают зависимости из общего контейнера и сами владеют своими детьми. Для приложения это рабочий обход, но не замена скоупам. Если вам нужны DI-управляемые скоупы, lifecycle-bound графы или выгружаемые фичи — это сигнал брать фреймворк.

**Где это вообще применимо.** Подход хорошо живёт, пока проект — одно-три модуля и команда, которая держит граф в голове. Раздел про библиотеки ниже — уже верхняя граница: дальше объём ручной проводки растёт, и в какой-то момент дешевле взять фреймворк.

## Как это масштабируется на библиотеки

Пока приложение — один модуль, composition root остаётся плоским. Но тот же подход растёт до отдельных KMP-библиотек, и там добавляется ещё один разрез: что библиотека показывает наружу, а что прячет.

### Разделение на Api и Impl

Библиотека делится на два модуля. Модуль **Api** содержит только интерфейсы и модели для внешнего использования. Модуль **Impl** зависит от Api и содержит все реализации.

Единственный модуль приложения, который зависит от **Impl**, — тот, где собирается DI. Остальные модули приложения и другие библиотеки зависят только от **Api**.

![Подключение Api и Impl](manual-di-api-impl.png)

Зачем разрез: он строго обозначает публичное API библиотеки и за счёт этого утоньшает интеграционный слой. Потребитель видит ровно то, что библиотека пообещала, и не может случайно опереться на реализацию.

### Публичный и внутренний контейнеры

У библиотеки контейнер раздваивается по видимости.

- **LibPublicContainer** — публичное API (фасад) библиотеки. В нём лежат все зависимости, которые библиотека отдаёт внешним потребителям.
- **LibInternalContainer** — наследник публичного, добавляющий зависимости для внутреннего использования. Внешним потребителям они не видны.

![Публичный и внутренний контейнеры](manual-di-public-internal.png)

```kotlin
// модуль Api
interface LibPublicContainer {
    val someRepository: SomeRepository
}

// модуль Impl
interface LibInternalContainer : LibPublicContainer {
    val someInternalService: SomeInternalService
}
```

### Точка входа в библиотеку

Контейнер кто-то должен собрать — выстроить платформенную часть, выдержать порядок инициализации. Эта сборка живёт в модуле Impl, за границей Api, и наружу торчит одной фабричной функцией:

```kotlin
// модуль Impl — виден только DI-модулю приложения
fun createLibContainer(config: LibConfigContainer): LibInternalContainer = LibContainerImpl(config)
```

Раньше у меня здесь был интерфейс `LibModule` с методом `create` и его реализацией. Это была привычка: «модуль» — слово, по которому в команде запоминали точку входа в библиотеку. Но если присмотреться, интерфейс с единственной реализацией, который вызывают статически, — ровно то, против чего возражает правило выше. Никто не держит `LibModule` полиморфно и не подменяет реализацию. Поэтому точка входа — обычная фабричная функция: граница Api/Impl уже прячет реализацию, второго интерфейса для этого не нужно.

Функция собирает реализацию внутреннего контейнера — она уже содержит все внутренние классы библиотеки, и каждый из них получил свои зависимости в конструктор. DI-модуль приложения — единственный, кто видит Impl, поэтому держит контейнер по внутреннему типу, а наружу отдаёт публичный фасад (повышающее приведение бесплатно):

```kotlin
class App {
    val lib: LibPublicContainer by lazy {
        createLibContainer(AndroidLibConfig(application = this))
    }
}
```

Дальше готовый контейнер достаточно прокинуть в конструкторы внешних потребителей:

```kotlin
val someInteractor: SomeInteractor by lazy {
    SomeInteractor(repository = lib.someRepository)
}
```

### Статический доступ изнутри библиотеки

Иногда внутренним классам библиотеки нужно достать контейнер статически — та же история, что с Android-компонентами, и та же честная оговорка: это локальный service locator на границе с фреймворком. Чтобы он не протёк наружу, типизируйте провайдер ровно на то, что нужно вызывающему. Внутреннему коду нужен внутренний контейнер — значит, и провайдер для него отдельный, внутренний:

```kotlin
// в библиотеке: внутренний провайдер, типизированный на внутренний контейнер
internal interface LibInternalProvider {
    val internalLib: LibInternalContainer
}

// в приложении один и тот же App отдаёт оба лица контейнера
class App : Application(), LibProvider, LibInternalProvider {
    private val container: LibInternalContainer by lazy {
        createLibContainer(AndroidLibConfig(application = this))
    }
    override val lib: LibPublicContainer get() = container          // наружу — публичный фасад
    override val internalLib: LibInternalContainer get() = container // внутрь — расширенный
}

// внутри библиотеки — один каст, и он громкий
class LibActivity : Activity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        (application as LibInternalProvider).internalLib.someInternalService.start()
    }
}
```

Честно про двойной каст. Если отдавать наружу только `LibProvider` с публичным типом, то изнутри пришлось бы писать `(application as? LibProvider)?.lib as? LibInternalContainer` — и это плохо: два разных промаха (хост не тот; контейнер вдруг не внутренний) гасятся в одну молчаливую ветку, внутренний `start()` просто не случается. Это ровно то «тихо отключили фичу», против чего весь подход. Отдельный внутренний провайдер убирает второй каст: остаётся один `as` (а не `as?`), который падает на старте с понятной ошибкой, если приложение собрано неправильно.

### Платформенный контейнер

Если у библиотеки много платформенных зависимостей, удобно вынести их в отдельный `LibPlatformContainer` и собирать контейнер композицией, а не наследованием. Это необязательный элемент: при малом числе платформенных зависимостей их объявляют прямо в `LibInternalContainer` и реализуют в его платформенных листах.

### Порядок инициализации

Сборка контейнера библиотеки идёт по шагам.

![Порядок инициализации DI библиотеки](manual-di-init-order.png)

1. Приложение реализует интерфейс конфигурации `LibConfigContainer` и отдаёт его в `createLibContainer`.
2. Библиотека создаёт платформенную реализацию `LibPlatformContainer` — свою внутреннюю сущность.
3. Из конфигурации и платформенного контейнера собирается полный контейнер, реализующий и публичный, и внутренний интерфейсы.
4. Приложение хранит его и отдаёт наружу: внешним потребителям — публичный фасад через `LibProvider`, внутренним классам библиотеки — расширенный через внутренний провайдер.
5. Дальше каждый пользуется контейнером по своему интерфейсу.

Дисциплина та же, что в приложении. Контейнеры не реализуют никаких посторонних интерфейсов: конфигурация и платформенный контейнер, попавшие в конструктор, — это детали реализации, а не часть публичного фасада.

## Ручной DI и разработка с ИИ-агентами

У наглядности есть второй потребитель, про которого пять лет назад не думали, — кодовый ИИ-агент. Tether я веду в связке с такими агентами, и ручной DI здесь оказался выгоден по той же причине, что и для человека: граф зависимостей лежит в коде явным текстом, без магии фреймворка.

Когда агент правит фичу, ему нужно понять, что куда передаётся. С ручным DI он это просто читает: конструктор — честный список зависимостей, точка сборки — один файл, любую связь видно через переход к определению. Фреймворк прячет половину этого за аннотациями и кодогенерацией — агенту приходится держать в голове правила фреймворка и достраивать невидимый граф по косвенным признакам. Чем меньше магии, тем меньше агент додумывает то, чего в коде не видно.

Отсюда же — проверяемость. Свод принципов ручного DI («зависимости — в конструктор», «не доставай из глобала», «синглтон создаётся один раз в корне») — это короткий чек-лист, по которому и человек, и агент-ревьюер сверяют новый код. В Tether этот чек-лист буквально оформлен как инструкция для агентов, что считать корректным DI. Ручной подход делает её исполнимой: проверять надо обычный код, а не поведение фреймворка.

## Фреймворк как запасная дверь

Ручной DI окупается до определённого масштаба. Дальше может начать болеть — и тогда переход на фреймворк станет осознанным решением конкретной проблемы. Сразу про статус честно: мы на ручном DI, остаёмся на нём и перейти пока не планируем. Фреймворк я держу не как пункт назначения, а как заранее разведанную запасную дверь — на случай, если упрёмся в то, чего ручной подход не даёт.

Где эта дверь — по моему опыту, не там, где обычно пугают. Ручной DI я носил в приложениях с четырьмя флейворами, двумя десятками библиотек и полусотней модулей, и единственное, что там реально мешало, — циклические зависимости. Причём это был скорее плюс: ручная сборка подсветила проблему архитектуры, которую стоило решать, а не прятать. Тут нужна оговорка: на ленивых полях `by lazy` цикл всплывёт не на компиляции, а в рантайме при первом обращении. Compile-time-фреймворк поймал бы его на сборке — раньше. Так что «циклы» — скорее довод за фреймворк, чем против.

Честные триггеры, при которых я бы взял фреймворк:

- **нужны скоупы и жизненный цикл зависимостей** — дочерние графы под экран, выгружаемые фичи, lifecycle-bound зависимости. Это то самое слабое место из «Границ подхода», и закрывать его руками — уже изобретать фреймворк.
- **проводка через границы модулей превращается в рутину** — когда модулей много и вклады из них собираются в контейнер вручную по одному и тому же шаблону.
- **граф перестал помещаться в голову** — и наглядность, главный плюс ручного подхода, больше не работает.

Пока ни один не сработал, фреймворк — лишний аппарат.

Какой именно — отдельный разговор, и для KMP критерии свои: поддержка всех таргетов, проверка графа на компиляции, эргономика в многомодульном проекте. Из живых вариантов я для себя разведал [Metro](https://github.com/ZacSweers/metro): KMP-first, проверяет граф на компиляции, работает компилятор-плагином.

Про «компилятор-плагин» стоит пояснить — это частый аргумент по скорости сборки. KSP (на нём, например, kotlin-inject) работает в два такта: сначала по символам генерирует Kotlin-код, потом компилятор компилирует и исходники, и сгенерированное. Компилятор-плагин (Metro на FIR/IR) выпускает код прямо внутри той же компиляции, без отдельного шага генерации. Отсюда «обычно быстрее» — особенно с ростом графа; гарантии на маленьком проекте нет.

Koin списывать со счетов нечестно: его Compiler Plugin (Koin Annotations) умеет проверять граф на компиляции, а `checkModules()` — на тестах. По умолчанию же Koin резолвит зависимости в рантайме, и для KMP это слабее: в приложении, где каждый таргет тестируется отдельно, «забыл зарегистрировать» рискует всплыть крашем на той платформе, что проверяли последней. Dagger и Hilt для KMP не подходят вовсе — они не мультиплатформенные.

Важно здесь не «какой фреймворк лучше», а что переход дёшев. Контейнеры и провайдеры — это уже почти граф: контейнер становится графом зависимостей, платформенные подклассы — вкладами в него, интерфейсы конфигурации — провайдерами значений, тесты на `open val` — графами с переопределённым связыванием. Это совпадение формы держится для фреймворков, которые строят граф из таких же вкладов (Metro, kotlin-inject со связкой Anvil); на Koin с его DSL переезд был бы скорее переписыванием. Но даже в лучшем случае — это работа на потом, и затевать её заранее смысла нет.

## Преимущества подхода

- **Наглядность.** Граф зависимостей — обычный Kotlin-код: видно, что и где создаётся, любую связь можно пройти в IDE. Никакой магии и объектов «из воздуха».
- **Честные конструкторы.** Сигнатура класса — это его полный список зависимостей. Ничего не приходит из невидимого глобала.
- **Структура подсказывает, где создавать компонент.** Дерево контейнеров повторяет дерево сорс-сетов, и место компонента — там, где впервые виден нужный API.
- **Тонкий интеграционный слой для библиотек.** Разделение на Api и Impl строго обозначает публичную поверхность.
- **Дешёвый переход, если упрётесь.** Контейнеры и провайдеры по форме уже близки к графу фреймворка — переезжать без структурной перетряски.

Ручной DI — это дефолт, который окупается бóльшую часть жизни проекта: пока граф помещается в голову и в IDE, вы платите за DI ровно столько кода, сколько он стоит, и видите его весь.

Идея не нова: фреймворкленый SDK-контейнер с делением на публичную и внутреннюю часть для KMM ещё в 2023-м описывал [Марцин Пекельны](https://medium.com/@maruchin/kmm-architecture-5-dependency-injection-79052c7ea778). Я добавил то, что держит подход на плаву за пределами игрушечного размера: иерархию контейнеров по сорс-сетам на всех платформах, паттерн провайдера для Android, честные границы и путь масштабирования на библиотеки.
