## Цель спринта

Завершить паринг на уровне протокола (CLI-флоу с PIN), подготовить продуктовую почву под следующий шаг по передаче файлов (`file-transfer.md` → `scoped`) и поднять инструментарий ревью. Параллельно — точечно закрыть два HTTP/discovery-бага, накопившихся к концу спринта 2. К концу спринта:

- паринг работает end-to-end из Desktop CLI: первое соединение → одинаковый 4-значный код в двух терминалах → подтверждение → передача разблокирована, повторное соединение паринг не запрашивает;
- продуктовая спека `file-transfer` имеет статус `scoped` и закрывает все open product questions — #8 (Android send UI) разблокирован для спринта 4;
- скилл code review через специализированных суб-агентов работает и применяется к новым PR — амортизирует затраты на ревью всех будущих задач;
- `FileClient` корректно выставляет `Content-Length` при известном размере файла, discovery перестаёт терять пиров на сетях с дубликатами имён сервисов.

## Полезный инкремент

После спринта:

1. **Паринг работает в Desktop CLI end-to-end** (#10) — фундамент верификации, заложенный в #9, наконец проверяется на сквозном пользовательском сценарии. Любой Android/iOS/Desktop клиент, который заговорит с CLI, сможет паримся по тому же протоколу.
2. **Продуктовый долг по `file-transfer` закрыт** (#107) — открытые вопросы по iOS picker, путям сохранения, поведению cancel, batch-семантике зафиксированы. #8 готов к старту без продуктовых пробелов; стартовая позиция для будущих iOS/Desktop send-задач тоже определена.
3. **Code-review скилл амортизирует все будущие PR** (#104) — специализированные суб-агенты дают консистентное качество ревью независимо от размера PR. Окупается уже на 3–4 крупных PR.
4. **HTTP-протокол передачи корректен** (#93) — `Content-Length` выставляется → совместимость с `curl` и стандартными HTTP-клиентами для отладки и интеропа.
5. **Discovery надёжнее** (#90) — пиры не теряются на сетях с дубликатами имён сервисов; меньше «исчезающих» устройств в `[peers]`.
